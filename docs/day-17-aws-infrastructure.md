# Day 17: Repeatable AWS infrastructure and deployment controls

## Infrastructure as code

[`infra/template.yaml`](../infra/template.yaml) is the AWS SAM/CloudFormation
stack for the currently implemented MVP services:

- API Gateway HTTP API routes public interest, engagement, church, devotion,
  and follow-up withdrawal requests to their Java 21 Lambda handlers.
- The leader engagement list and review routes use the Cognito JWT authorizer
  with separate `saved2serve/leader.read` and `saved2serve/leader.write`
  scopes. `LeaderEngagementApiHandler` still checks the `Leaders` group; do
  not treat scopes as group membership.
- A single on-demand DynamoDB table has the three application indexes
  (`StatusCreatedAtIndex`, `AreaCreatedAtIndex`, and `EmailHashIndex`),
  point-in-time recovery, and customer-managed KMS encryption. The table and
  key are retained when the stack is deleted or replaced. There is no TTL.
- A standard SQS follow-up queue is encrypted with SQS-managed keys, has a
  bounded redrive policy and DLQ, and enables partial batch failure handling.
- Cognito allows administrator-created users only, provisions a `Leaders`
  group and the two custom API scopes, and configures a public authorization
  code client for the leader portal. MFA is available but optional; enable or
  require it according to the operator's account policy before production.
- SES is restricted in the worker role to the configured sender identity.
  The configured email identity must be verified in SES, and the account must
  be out of the SES sandbox to send to unverified recipients.
- A generated unsubscribe signing secret is passed only to the two functions
  that use it. No application secrets or credentials belong in source control
  or template parameters.
- API access logs contain request ID, route key, status, and response length
  only. Lambda log groups have 30-day retention; never add request bodies,
  authorization headers, queue payloads, emails, or engagement content to
  access/application logs. Structured application events, the operations
  dashboard, actionable alarms, and the incident runbook are described in
  [Day 18 observability](./day-18-observability.md).

The template intentionally exposes no admin routes that are not implemented
by this codebase. It does not create a public S3 bucket or static website
hosting; static site hosting is a separate deployment surface. It does not
seed churches or devotion links, set a personal-data retention period, or
delete data automatically.

## Deployment

Prerequisites: AWS SAM CLI, AWS CLI credentials for the intended account and
region, and a verified/approved SES sender. Do not deploy to a production
account until the stack change set and IAM permissions have been reviewed.

From the repository root, supply exact browser URLs/origin and unique hosted
login prefix. URLs containing commas are not supported by the
`CommaDelimitedList` parameters. Choose a CloudFormation stack name no longer
than 39 characters because the template uses explicit Lambda function names
with service-specific suffixes.

```powershell
aws sts get-caller-identity
sam validate --lint --template-file infra/template.yaml
sam build --template-file infra/template.yaml
sam deploy --guided --template-file .aws-sam/build/template.yaml
```

For a repeat deployment, record the selected parameter values in the
operator's approved deployment system, not in a committed environment file.
Review the generated CloudFormation change set before execution. The signing
secret is generated by Secrets Manager. Do not pass it in CLI arguments or
print it in logs. Dynamic references resolve the value into the two Lambda
environment configurations; restrict Lambda configuration-read access to
trusted operators and keep it out of deployment output.

Use the stack outputs to configure the frontend deployment's `web/config.js`:
`ApiBaseUrl`, `CognitoHostedUiDomain`, and `CognitoAppClientId`, along with the
exact deployed leader-portal callback and logout URLs. Keep those values
consistent with the callback/logout and CORS parameters used to create the
stack.

The Java handler sources are packaged by SAM's Maven builder from the
repository-root `pom.xml`. The template does not configure a Lambda URL,
public self-registration, broad API CORS, a public DynamoDB table, or IAM
wildcards for data, queue, KMS, or SES access. API Gateway throttling is set
to a modest stage default and should be tuned from observed MVP traffic.

## Deployment permission review

Use a dedicated deployment principal or CloudFormation execution role scoped
to the target account, region, stack, and this resource set. Its permissions
must cover the CloudFormation-managed resource lifecycle, artifact upload to
the chosen SAM deployment bucket, and `iam:PassRole` only for the execution
roles created by this stack. Do not attach administrator access or use a
wildcard `iam:PassRole` grant. If the account requires a permissions boundary,
apply it to all generated Lambda execution roles.

Before granting deployment access, verify the identity with
`aws sts get-caller-identity`; review the change set; and use
`aws iam simulate-principal-policy` against the deployment principal for the
required CloudFormation, Lambda, API Gateway, DynamoDB, Cognito, SQS, SES,
KMS, Secrets Manager, CloudWatch Logs, and scoped PassRole actions. A
successful template validation does not prove the caller has these
permissions. This repository change does not deploy AWS resources or verify
an AWS account's effective IAM policy.

The repository's manual, reviewed GitHub Actions deployment flow is described
in [Day 19 deployment workflow](./day-19-deployment-workflow.md). It uses
GitHub OIDC and a protected `production` environment; it does not deploy
automatically on every push.

## Verification checklist

1. Run `sam validate --lint --template-file infra/template.yaml` and
   `sam build --template-file infra/template.yaml`.
2. Inspect the change set for the expected HTTP methods/paths, public versus
   protected route authorizers, table indexes, queue redrive configuration,
   and separate function roles. Reject any unplanned destructive replacement.
3. Confirm the SES identity is verified; after deploy, verify user-pool issuer,
   app-client audience, hosted domain, exact callback/logout URLs, and custom
   scopes.
4. Verify public routes work without a token. Verify leader routes reject
   missing/invalid tokens and wrong scopes, and that a correctly scoped user
   outside `Leaders` is denied by the handler.
5. Inspect each Lambda role to confirm only its required table/index actions,
   KMS operations, queue actions, SES sender, and log group are granted.
6. Confirm no logs contain request bodies, access tokens, emails, queue
   payloads, or submitted engagement content. Check queue retries and DLQ
   alarms/operations before enabling follow-up delivery for real recipients.
7. Confirm backups and retention ownership before stack teardown. The table
   and KMS key are retained; their lifecycle requires an explicitly reviewed
   operator procedure.

Application contracts and focused handler tests remain documented in the
corresponding Day 6 through Day 16 documents. In particular, verify the
Day 12 consent, withdrawal, generic SES-content, and retry boundaries and the
Day 10/11 JWT scope plus `Leaders` group checks.
